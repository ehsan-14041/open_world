# Cross-event diagnosis — is the failure in the model or in the measurement?

> Generated by `python scripts/replay_port_event.py --cross-event --write-report`. The world model was **frozen** across both replays: no coefficient, lag, polarity or topology was changed between them.

## Why a second event was necessary

The Yantian 2021 replay produced a large timing error (-9 weeks). A single event cannot distinguish two explanations:

1. **The model is wrong** — its post-shock persistence is too weak, so everything peaks and recovers too early.
2. **The measurement was wrong** — the only obtainable observable was a global monthly aggregate standing in for a single-port weekly variable.

A second event, chosen to differ on every dimension that could produce a spurious result, separates them.

| | Yantian 2021 | Baltimore 2024 |
|---|---|---|
| Year | 2021 | 2024 |
| Region | South China | US East Coast |
| Trigger | COVID labour absence | physical channel blockage |
| Background regime | global congestion wave | normal conditions |
| Capacity loss | to ~30% of normal | to zero |
| Duration | ~4.5 weeks | ~11 weeks |
| Observable tested | global monthly delay (proxy) | dated local restoration milestones |
| Capacity path | injected in phases | **model output** |

The two replays share no data source, no observable and no measurement method.

## Bias metrics

A single R² or MAE cannot express the thing that matters for a disruption model — whether its clock runs at the right speed. Two Event-Simulator-specific metrics:

| Metric | n | Errors (turns) | Median | Episodes | Verdict |
|---|---|---|---|---|---|
| `peak_timing_bias` | 1 | -9 | **-9** | yantian_2021 | no consistent bias |
| `recovery_bias` | 1 | -6 | **-6** | baltimore_2024 | no consistent bias |
| `combined_timing_bias` | 2 | -9, -6 | **-6** | baltimore_2024, yantian_2021 | systematically early |

- **peak_timing_bias** — simulated peak turn - observed peak turn, per test. Negative means the model peaks EARLIER than the real world did.
- **recovery_bias** — simulated recovery turn - observed recovery turn, per test. Negative means the model recovers EARLIER than the real world did.
- **aggregation** — reported as the median across all scored tests in all events. A median that is consistently negative across independent events is a systematic clock error, not noise — random model error would change sign between events.

**median timing bias -6 turns across 2 scored tests in 2 events.**

## Verdict

- Scored timing tests: **2**
- Tests where the model was too early: **2**
- Tests where the model was too late: **0**
- Episodes showing the early bias: **baltimore_2024, yantian_2021**
- Pattern repeats across independent events: **YES**

**Every timing error in both events has the same sign: the model is too fast.** That bias survives a change of year, continent, trigger, background regime and — most importantly — of measurement method. It is therefore not an artefact of the Yantian proxy alone.

### What this does NOT establish

- Baltimore's **hard observed milestone (week 11) is INSIDE the simulated envelope** — about a third of the tested worlds were that slow or slower. The model's *central* case is 6 weeks early, but its assumption range does contain the truth. That is a biased median, not a strict falsification.
- The only Baltimore test falling strictly outside the envelope is `normal_operations`, and that milestone is recorded as **reported, not observed** (an expectation published before the fact), so it is deliberately excluded from the scored count.
- Two events is a pattern, not a proof.

So the honest statement is: **a consistent directional bias, reproduced on an independent event and an independent measurement method — not yet a strict falsification.**

## Competing structural hypotheses

The bias is consistent with the topology lacking an accumulating stock. The model is shaped `shock → propagation → relaxation`, so when the shock is released every variable begins returning to baseline immediately. The real sequence appears closer to `shock → queue accumulation → congestion → downstream backlog → capacity returns → backlog keeps propagating → delayed peak → clearing`. **A reopened port is not a cleared queue.**

| # | Hypothesis | Mechanism | How it would be tested |
|---|---|---|---|
| H1 | **Queue as a stock** | A `vessel_queue` stock accumulates while capacity is below demand and drains at a finite rate afterwards, so delay persists after capacity has recovered. A reopened port is not a cleared queue. | fit the drain rate on one event, predict the other event's recovery week out-of-sample |
| H2 | **Backlog persistence** | `order_backlog` already exists but relaxes toward causal pressure rather than integrating a flow imbalance. Making it a true stock would delay downstream peaks without changing any effect size. | same held-out design; compare against H1 on the same events |
| H3 | **Lag structure understated** | Effect sizes are roughly right but every declared lag is too short. | re-estimate lags only, leaving effect ranges frozen |
| H4 | **Recovery asymmetry** | Onset and recovery currently share one `response` parameter per variable. Real recovery is plausibly slower than onset. | split into separate onset and recovery rates; check whether onset timing degrades |

**None of these has been implemented, and no coefficient was changed.** Adopting one now — on two events, with the fitting window equal to the evaluation window — would be exactly the overfitting this project has already documented once (`docs/FITTING_FINDINGS.md`).

## What this replaces

The Yantian report concluded the failure was most likely the measurement. Baltimore removes that as a *sufficient* explanation: the same bias appears with a completely different measurement method, on a variable the model actually outputs rather than one we injected. The measurement problem is real and remains the binding constraint on validation, but the structural hypothesis is now at least as credible.

## Next experiment

1. Add a **third** disruption with a locally observed series, not just milestones.
2. Implement H1 and H2 as *alternative* modules, leaving the current module untouched.
3. Fit each candidate on one event and evaluate on a **held-out** event.
4. Adopt a structural change only if it improves held-out timing error, and record it as a calibration record with its prior preserved.
