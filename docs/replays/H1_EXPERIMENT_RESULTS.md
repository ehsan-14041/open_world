# H1 experiment results — vessel-queue stock vs frozen baseline

> Generated by `python scripts/run_h1_experiment.py --write-report`. Acceptance criteria were fixed in [H1_EXPERIMENT_PROTOCOL.md](H1_EXPERIMENT_PROTOCOL.md) **before** these results existed, and are evaluated in code rather than in prose.

## Headline

**Verdict by the pre-registered rule: `experimental_no_effect`** — four of the five criteria pass; criterion 1 fails.

That label understates what happened, and the discrepancy is itself the most interesting result of this experiment. See [§7](#7-the-rule-and-its-flaw).

## 1. What was changed

```
BASELINE       port_capacity ──(linear, lag 0–1)──▶ shipping_delay

EXPERIMENTAL   port_capacity ──(conservation)──▶ vessel_queue ──(linear, lag 0–1)──▶ shipping_delay
```

One new variable, one edge replaced by two, one new axis. Everything downstream of `shipping_delay` is untouched, and every other edge keeps its polarity, effect range and lag exactly.

**New variable** — `vessel_queue`, a stock in *normal-flow-weeks of unprocessed arrivals*. That unit was chosen because converting to vessels or TEU would need a conversion factor no data supports for these events.

**New parameters** (three, one definitional):

| Parameter | Value / range | Evidence status |
|---|---|---|
| arrivals (`inflow`) | 1.0, fixed | definitional — makes the queue exactly 0 in steady state |
| clearance surge | 1.05 / 1.15 / 1.35 | `expert_assumption`, swept |
| `vessel_queue → shipping_delay` | 0.08 / 0.15 / 0.25 | `expert_assumption`, swept |

H1 being independently supported does **not** make these supported. They are assumptions with predeclared ranges, swept rather than fitted.

## 4. Does recovery slowness emerge, or was it imposed?

It emerges. Nothing in the experimental module contains a recovery delay constant — a test asserts the absence of one.

**yantian_2021**

- queue starts accumulating once capacity drops, peaks at **2.01 flow-weeks in week 7**
- capacity is back above 95% in **week 7** — and the queue is still **2.01** at that moment
- `shipping_delay` therefore peaks later, in **week 9**
- the queue is still draining at the end of the window (1.66)

**baltimore_2024**

- queue starts accumulating once capacity drops, peaks at **1.63 flow-weeks in week 5**
- capacity is back above 95% in **week 5** — and the queue is still **1.63** at that moment
- `shipping_delay` therefore peaks later, in **week 8**
- the queue is still draining at the end of the window (0.86)

This is the mechanism doing exactly what H1 says it should: *a reopened port is not a cleared queue*.

## 5. Failure modes and unexpected behaviour

- **The queue does not fully clear inside either window.** With central clearance surge (1.15) the drain rate is only 15% of nominal throughput per week, so a two-week backlog takes many weeks to work off. This is reported rather than tuned away: the surge range was predeclared, and shortening the drain by raising it would be exactly the retuning this experiment forbids.
- **Yantian's first divergence is unchanged at week 0**, because it comes from the no-hindsight baseline (the only admissible pre-cutoff value was 0.30 days above the actual May level). No dynamics change can fix an initial-condition offset.
- **No magnitude blow-up appeared**, which was a live risk: replacing the direct capacity→delay edge with a queue-mediated path could have over- or under-shot. It undershot slightly less than the baseline overshot.

## 6. Anti-retuning confirmation

- One shared configuration across both events — the same module, the same swept grid. Per-event parameter values are impossible by construction and are asserted by a test.
- No baseline coefficient, lag, polarity, baseline level, scale or response changed; the frozen-module regression tests still pass.
- The baseline replay reports reproduce identically.
- H2 was not implemented: `order_backlog` is still a relaxation variable, and no downstream lag or effect range moved.

## 7. The rule, and its flaw

| Criterion | Result |
|---|---|
| 1 combined timing moves toward zero by 2 or more | **FAIL** |
| 2 sensitive events improve insensitive not degraded | PASS |
| 3 direction validity preserved | PASS |
| 4 no magnitude blow up | PASS |
| 5 no retuning one shared config | PASS |

Criterion 1 gated on the **combined median** timing bias. With only two scored tests — one of which the protocol itself predicted would be mechanically frozen — the median of {−5, −6} is −5, so a 4-turn improvement on the only metric that could move shows up as a 1-turn movement in the aggregate.

**That was a bad choice of aggregator, and it was my own.** The protocol correctly predicted Baltimore's insensitivity and then still gated on a statistic that averages it in. The rule is nonetheless applied as written: changing an acceptance criterion after seeing results would destroy the only thing pre-registration is for.

The correct response is to fix the aggregator **for the next experiment, in advance** — e.g. gate on the median over *mechanically sensitive* tests only, declared per experiment — not to re-score this one.

## 8. Verdict

### `experimental_no_effect` by the pre-registered rule

The substantive finding, stated plainly and separately from the label:

> **An independently supported queue-stock mechanism explains a substantial part of the simulator's timing bias on the only event able to test it** — peak timing error −9 → −5 weeks, peak magnitude error +3.3 → +1.4, envelope coverage 0.00 → 0.50, correlation −0.15 → +0.69 — **while leaving the second event's metric untouched, as predicted, because that metric cannot see the mechanism.**

So the answer to the task's question — *does an independently supported queue-stock mechanism explain part of the previously measured timing bias?* — is **partially, on the evidence available**, and the evidence available is one event.

## 9. Consequences

| Item | Status after this experiment |
|---|---|
| H1 hypothesis | `experimental_no_effect` by the rule; substantive improvement recorded |
| Known defect *recovery dynamics too fast* | stays **`known`** — not `mitigated` |
| Default production model | **unchanged**. Do not merge. |
| Historical validation | still blocked — needs a held-out event |

**The evidence does not yet support changing the default production model.** One event moved; one could not. Promoting a mechanism on a single sensitive observation would repeat the mistake this project has already documented twice.

## 10. Next step

1. Pre-register a better aggregator (sensitivity-weighted) for the next experiment.
2. Find an event whose *downstream* metric can move — the same event #3 problem, now with a sharper requirement: it must have a delay or queue observation, not just a capacity milestone.
3. Only then can H1 be evaluated out of sample and the defect move to `mitigated` and eventually `historically_validated`.
